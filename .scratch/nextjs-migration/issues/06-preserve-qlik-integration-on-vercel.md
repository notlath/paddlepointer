Decision: Keep Qlik Cloud as a read-only analytics copy. Reimplement the existing four analytics REST feeds and staff-only impersonation token exchange as Next.js Route Handlers, preserving their public paths and contracts with compatibility rewrites where needed. On Vercel Pro or Enterprise, a protected one-minute Cron Route Handler drains a durable reload-pending marker into the existing optional Qlik triggered automation; Qlik's scheduled 15-minute Event-hours reload remains the backstop. On Hobby, omit the optional minute trigger and use the Qlik schedule. See [ADR 0014](../../../docs/adr/0014-keep-qlik-rest-feeds-on-vercel.md).

## Question

How should the app preserve Qlik's read-only access to event and match data, staff token exchange, and optional reload trigger after PHP is removed and the app runs on Vercel? Decide whether to keep compatible REST feed routes or replace them with another supported contract, where secrets and authorization live, and how scheduled or batched reload triggering works without changing Qlik's analytics role.

## Feed and token contracts

- Preserve GET `/api/qlik/get-events.php`, `/api/qlik/get-matches.php`, `/api/qlik/get-leaderboard-results.php`, and `/api/qlik/get-leaderboard-players.php` as Qlik-facing URLs using Next.js Route Handlers or rewrites to them. Preserve `X-Analytics-Key`, the optional `event` filter, status/error behavior, row fields and ordering, UTC timestamp formatting, and all-Events default. A missing configured key or invalid header fails closed; do not accept credentials in query strings. Never include Visitor Matches or account/private Visitor data.
- Project those feed rows from the authoritative PostgreSQL Event, Tournament Match, Match, Player, and Rally records. Keep scheduled Tournament Match and Player rows, finished non-Visitor result rows, eligible standalone Matches, current/past Event flags, and existing Rally summary rules. Rebuild legacy response shapes at this boundary rather than storing a second legacy JSON record. Qlik continues to pull and calculate; it never writes PaddlePointer data. The Live Board stays on PaddlePointer data and does not wait for Qlik reloads.
- Preserve GET `/api/qlik/get-embed-token.php` for the current staff analytics client even though its UI is now native and QIX-backed. Verify the current Better Auth session and staff role on every request. Exchange server-held Qlik M2M credentials for a short-lived user-impersonation token for the dedicated Event Viewer subject. Preserve the `{ ok: true, accessToken, expiresIn }` response and the signed-out 401, non-staff 403, and upstream-failure 502 behavior. Do not return the client secret, shared analytics key, refresh token, or automation execution token.
- Keep `ANALYTICS_KEY`, `QLIK_M2M_CLIENT_ID`, `QLIK_M2M_CLIENT_SECRET`, `QLIK_EVENT_VIEWER_SUBJECT`, optional `QLIK_RELOAD_TRIGGER_URL`/`TOKEN`, and `CRON_SECRET` in server-only Vercel environment settings per environment. Set `QLIK_TENANT_URL` and the matching public Qlik tenant/app configuration for the native analytics client in each environment; the tenant origin is public, but M2M credentials are not. Configure Qlik's allowed browser origins and REST connector URL/header at the matching production domain. Preview/staging must not trigger production Qlik reloads or write into its production analytics copy.

## Reload scheduling

- A successful commit that changes a feed-visible Event, Schedule, finished Match, Rally-derived result, or Player identity marks a new durable pending token in the same PostgreSQL transaction. Visitor-only and failed writes do not mark it. No Qlik network call runs in the scoring request. The marker is the compare-and-clear token from ticket 04, so a newer write remains pending if it lands during a reload attempt.
- When optional triggering is enabled, configure a Vercel Cron GET route every minute (`* * * * *`) in production. Require a configured `CRON_SECRET` Bearer header and fail closed if it is missing or wrong. The handler claims a short database lease before calling the existing Qlik triggered automation with its server-held execution token; overlapping or duplicate Cron invocations must not start concurrent reloads. On confirmed acceptance, clear only the token claimed before the call. On failure, preserve pending state and let the next Cron run retry. An ambiguous timeout may cause a duplicate request; do not claim exactly-once delivery.
- Keep the Qlik Cloud 15-minute scheduled reload during Event hours as an independent backstop, including when the optional trigger is not configured. Vercel Cron runs against production in UTC and does not retry failed invocations. Vercel Hobby cannot deploy a one-minute Cron schedule; if production uses Hobby, omit that Cron entry and rely on Qlik's schedule. Confirm the production plan and Qlik schedule as release prerequisites, and monitor Cron failures and the age of pending reloads.

## Delivery checks

- Contract-test every feed against representative migrated records, including filtered/unknown Events, scheduled slots, finished standalone Matches, Player names after rename/merge, Rally summaries, Visitor exclusion, key refusal, and exact legacy response shape. Compare the resulting Qlik load to the current feed before cutover.
- Test the exact staff token response and 401/403/502 behavior, secret redaction, Cron secret refusal, pending-marker coalescing, overlapping/duplicate Cron calls, a write arriving during the Qlik call, failure/timeout retry, and the scheduled-reload fallback. Rehearse a production-like reload against staging Qlik resources before switching the connector URL.
