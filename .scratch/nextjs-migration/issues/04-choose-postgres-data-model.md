Decision: Reshape the MySQL records into a relational PostgreSQL domain schema managed by Drizzle. Store one Event and its one Tournament as linked rows; model the Schedule, Tournament Matches, scored Matches, Players, and stable account relationships as records with keys and constraints. Keep only the ordered Rally log and genuinely variable payloads in JSONB, never a second authoritative full Match or Tournament document. See [ADR 0010](../../../docs/adr/0010-postgres-domain-schema-with-jsonb-rally-log.md).

## Question

Should the migration preserve the current table structure and JSON payloads as closely as possible, or reshape selected records into a more relational PostgreSQL model? Decide how events/tournaments, tournament matches, finished matches, players, accounts/sessions, and app settings map to PostgreSQL, including which JSON fields remain and what integrity constraints are required. Base the choice on the selected ORM and data-access boundary.

## Logical mapping

- `events` holds durable Event identity, name, timestamps, and lifecycle metadata. `tournaments` has a required, unique Event foreign key and holds format and court configuration. Application operations create and delete the Event–Tournament pair transactionally; the unique foreign key prevents two Tournaments for one Event, while the application must not expose a bare Event row. Keep all past Events. A singleton `application_state.current_event_id` foreign key identifies the Current Event rather than a mutable flag on every Event.
- `tournament_players` records each Tournament roster membership by Player ID. `rounds` belongs to a Tournament and carries its order. `tournament_matches` belongs to a Round and records court, schedule order, assigned Teams, and scheduling state before play. `tournament_match_players` records the two Teams' ordered Player IDs for each scheduled slot. Once play starts, the linked `matches` row alone owns live/final scores, winner, Match lifecycle state, and timing; the Live Board derives the slot's playing/completed state from it. This replaces the full `tournament_json`, team JSON, and `match_json` copies as sources of truth.
- `matches` stores in-progress and finished scored Matches, their scope (`tournament`, `standard`, or `visitor`), optional Event and Tournament Match links, scorer/owner account link where known, status, target and live/final scores, winner, timing, and other stable scoring facts. A Tournament Match links to at most one scored Match. `match_participants` stores ordered Team membership: Player foreign keys for MTC Matches, and local names without Player IDs for Visitor Matches. Visitor Matches have a verified Visitor account owner and no Event or Player link; historical standalone MTC Matches may have no Tournament Match or Event link.
- `players` is the lasting Player directory, with a unique normalized name and nullable Skill level. A Player needs no account. `app_accounts` has a one-to-one link to the Better Auth user for role and active status, plus an optional unique Player foreign key. Better Auth owns its own user, credential account, session, and verification tables through Drizzle; do not migrate legacy session tokens. Preserve a reviewed legacy-ID mapping during import, but keep migration identifiers out of the domain relationships.
- The singleton `application_state` row holds typed operational settings: `current_event_id` as an Event foreign key and a nullable `qlik_reload_pending_token` UUID. Each qualifying write replaces the token; after a successful Qlik reload, the worker clears it only if it still equals the token it read, so a newer write remains pending. Secrets remain in server-side environment configuration, not these tables.

## JSONB and integrity

- `matches.rally_log` is a JSONB array of Rally events in play order. PostgreSQL preserves array element order; the application validates each Rally shape, sequence, and the existing event-count limit before saving. No other JSONB field is planned; add one only when a concrete variable payload requires it and its schema and owner are documented. Do not store duplicate authoritative scores, rosters, or full Match/Tournament snapshots in JSONB. Rebuild legacy API and Qlik payloads from relational records plus the Rally log at compatibility boundaries.
- Primary keys and foreign keys protect Event–Tournament–Round–Tournament Match–Match and Player/account links. Unique constraints protect at most one Tournament per Event, the singleton settings row, normalized Player names, one account per Player, one scored Match per Tournament Match, `(round_id, court)` scheduled slots, and Team position per scheduled/scored Match. Check constraints protect allowed status/scope/team values, nonnegative scores, valid court/round/position numbers, Visitor scope/owner/Event consistency on each Match row, and `jsonb_typeof(rally_log) = 'array'`. Index Event, Match status/timestamps, owner, and Player links used by Live Board, History, Leaderboard, and Qlik reads.
- Enforce relationships that span multiple rows, such as a Tournament Match and scored Match belonging to the same Event, inside the server's bounded transactions and with composite keys or database constraints where practical. Do not let migration import orphaned links or silently invent Player identities for Visitor names. Derive match/completion counts from authoritative rows unless a measured read need justifies a maintained projection.

## Delivery gates

- Write the exact Drizzle schema and reviewed SQL migrations from this logical model, including explicit deletion behavior, indexes, and any database constraints needed for cross-row invariants.
- Rehearse import on representative MySQL data. Compare Event, Tournament Match, Match, Rally, Player, account-link, and settings counts and references; validate score/Rally integrity, Visitor isolation, and Qlik feed parity before cutover.
